# Smashcraft

- Follow README's "Principles": if a task seems to need memory reads, disassembly, decompiled code or Blizzard's or Nintendo's files in the repo, stop and measure from outside instead.
- Keep Wisp changes in Wisp; consume its published pin via the updater. Never edit installed dependencies or add a framework copy.
- The roster holds at 26 until every fighter feels good; each has a specific personality; prefer Warcraft models.
- Classic models only: never add Definitive Edition support, code, assets, checks or docs (see docs/design/roster.md).
- Every frame must sustain 60 fps; the map’s own work gates at p99 ≤ 10 ms and worst frame ≤ 14 ms (Warcraft draws inside 16.7 ms), and a gate miss remains unfinished work. A worst frame over 10 ms and up to 14 ms is a soft target: it lands with a `Target-debt:` trailer.
- Keep every mutable gameplay field in deterministic snapshots/replay; local presentation stays separate and shared handles are created consistently.
- Publish a release only when Tom decides; private builds keep the next release's version plus the count of first-parent commits since the last release tag (Smashcraft 0.1.1-dev.830), and release candidates are Smashcraft 0.1.1 RC-N from a v0.1.1-rc.N tag. Diagnostics keep distinct run IDs and names; keep one current candidate under Maps/00-Smashcraft.
- Never touch Tom’s install; run account a solely as clone-a through its launch.sh, which yields to Tom’s game.
- A visual box (stage, water, fog, lighting, portrait, VFX, animation, HUD) closes only on captures from Tom's own profile in Classic on the VM pool. A VFX, animation or move-readability box also needs a motion strip, not a still; the effect's footprint matching the hit regions on the active frames; and a cold reader new to the move, shown it on the strip's stage, naming what it does and where it hits. Wisp renders, 3.0.1 captures and "the effect spawns" are evidence, not acceptance (#277, #428, #433).
- Run evidence (captures, logs, results) goes to ~/.local/state/smashcraft/evidence/<run>, never into the repo; evidence/ is gitignored, and runs before this change are in git history as `smashcraft:evidence/<run>`.
- Every move and Tom-facing build meets [the finished-move bar](docs/design/finished-move.md) whether or not its issue says so; the Tom-facing gate refuses a build that misses a line.
- Place every change by [docs/architecture.md](docs/architecture.md)'s "Where things live" table; sim code never imports presentation, render, ui, platform or shell.
- Per-fighter data goes in that fighter's own files, never a new row or `character ===` branch in a shared all-fighter table or engine file.
- Generated files (first line `Generated by <producer>`) are regenerated by their producer, never hand-edited.
- A new Fighter field is one row in `sim/state/fighterSchema.ts` once S1 lands; until then edit every mirror the architecture table lists.
- Controller actions, keys and thresholds are defined once in `ts/src/game/input/` and `sim/stickZones.ts`; the plug-in and padbridge read them, never restate them.
- A new finding goes onto its existing epic (#7, #8, #9, #13 under the 0.1.1 root #66) or the After 0.1 issue (#14) as a checkbox or comment, and a new issue is opened only for a new ship-blocker or when Tom files it.
